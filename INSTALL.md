# Распаковка личной системы из GitHub

Это инструкция установочному агенту Work. Она описывает установку из чистых исходников, а не установку глобального навыка. Выполни подготовку, развертывание и выдачу файлов; не заканчивай только обсуждением плана. Используй доступный поддерживаемый процесс Sites.

## 1. Получить исходники и зафиксировать режим

Источник: https://github.com/bymaksimenko-stack/gruppa-rosta-personal-system . Получи текущий main из GitHub в новую облачную рабочую папку. Назови фактический remote и полный commit. Не используй папку разработчика, прежний облачный клон, локально установленного НОРДа или данные другого чата как доказательство чистого запуска.

Сначала прочитай AGENTS.md, README.md, docs/DECISIONS.md, docs/ARCHITECTURE.md, docs/DATA_AND_PRIVACY.md и docs/UPDATES.md. Прочитай все четыре файла project/. Выполни `npm run check:template` и `npm run package:project` до регистрации Site. Эти две проверки не требуют установки npm-зависимостей; нужны Node.js и Python 3. Если чего-то нет, назови конкретный недостающий компонент, не объявляя проверку успешной.

В режиме «чистый тест» создается одна новая тестовая личная копия. Эталонный hosting.json должен быть без project_id. Если скачанная копия уже содержит личный project_id, останови регистрацию и выясни источник привязки; не удаляй идентификатор ради создания еще одного сайта. Прежние Sites и их базы не трогай.

Если продолжаешь уже начатую установку в этой рабочей папке, используй ее сохраненный project_id и статус. Не создавай новый Site при повторе команды или неопределенном результате регистрации. Сначала выясни, завершилась ли предыдущая попытка. Это правило важнее требования «новый» при возобновлении того же прогона.

## 2. Развернуть готовый код через Sites

Нужен приватный Site с серверным хранением D1 и MCP. Используй готовые app/, lib/, db/, миграции и бренд-материалы репозитория. Не создавай заново похожий статический макет и не заменяй D1 на localStorage. HTML fallback — отдельный ручной сценарий.

Для исходников из GitHub применяй поддерживаемый Sites-процесс сохраненного шаблона. Следуй актуальной инструкции Sites в текущей среде: подготовка с template-source, окружение, регистрация, установка зависимостей, сборка, синхронизация исходников и публикация. Не подставляй абсолютные пути с чужого компьютера. Не копируй Git metadata, секреты, идентификаторы прежних Sites, runtime и локальную базу в новый шаблон. Сохрани готовый код и d1/capabilities из hosting.json.

Для первого чистого теста зарегистрируй один Site с названием «ГРУППА РОСТА | ТЕСТ РАСПАКОВКИ»; для обычного участника — «ГРУППА РОСТА | ЛИЧНАЯ СИСТЕМА». Сразу сохрани возвращенный project_id в личном hosting.json. Он не должен попасть в общий GitHub-репозиторий.

Установи зависимости из lockfile поддерживаемым установщиком Sites. Выполни `npm run check` и production build по инструкции Sites. Не меняй опубликованные миграции. Опубликуй приватно; дождись подтвержденного успешного результата и URL. При ошибке читай диагностику и исправляй ее в этой же копии. Если механизм публикации недоступен, выдай подготовленные файлы и точный незавершенный этап, а не выдуманный адрес сайта.

Используй связанный с новым Site MCP-плагин. Желаемое имя — «ГРУППА РОСТА | МОИ ДАННЫЕ»; если Sites назначил другое, сообщи фактическое имя и ссылку подключения. Не создавай отдельный сервер данных или дополнительный MCP-плагин поверх Site. Глобальные навыки через Plugin Creator и локальные marketplace не устанавливай.

## 3. Проверить именно новую копию

Проверь опубликованный MCP endpoint по документации Sites: объявление сервера, обнаружение и список инструментов. Отличай проверку HTTP endpoint от наличия инструментов в конкретном чате.

Установочный чат может видеть старый личный плагин с такими же суффиксами инструментов. Не вызывай его для доказательства работоспособности новой базы. Сначала установи соответствие подключения идентификатору или URL только что созданного Site. Если это не удается доказать, отметь проверку чтения новой базы как невыполненную и дай владельцу ссылку подключения нового плагина. Название инструмента само по себе не доказывает принадлежность.

Если подключение нового Site доступно и однозначно, вызови `gruppa_rosta_v1_get_nord_context` и `gruppa_rosta_v1_get_dashboard`. Проверь согласованность данных и неизменность ревизии после повторного чтения. Для чистой копии содержательные личные цели, планы и память не должны быть перенесены из прошлых тестов. Названия разделов и стартовые значения интерфейса не считай биографией.

Ничего не записывай от имени участника ради теста. Если понадобилась проверка записи, сначала покажи конкретную техническую запись и получи разрешение. Развертывание системы не является разрешением заменить реальные цели тестовыми.

## 4. Выдать файлы и точные действия участника

Выдай отдельными скачиваемыми файлами:

1. `01 - ГР - НОРД.md` — полная инструкция первого специалиста.
2. `02 - ГР - РИТМ.md` — полная инструкция второго специалиста.
3. `Настройки проекта.md` — текст для поля инструкций проекта.
4. `Как начать.md` — порядок запуска и проверки.

Выдай также ZIP, полученный package:project. Не меняй русские имена внутри архива: на них ссылается общая инструкция. Если механизм вложений меняет имена, предложи распаковать ZIP. Если выдача вложений недоступна, дай реальные ссылки на конкретные файлы GitHub; не выдавай внутренний путь рабочей среды за скачиваемый файл.

Попроси участника выполнить ровно следующие действия в уже созданном облачном проекте:

1. Добавить два распакованных файла специалистов в Sources / «Источники» проекта.
2. Скопировать текст между разделителями из «Настройки проекта.md» в поле «Инструкции проекта».
3. Открыть первый новый чат в этом проекте, подключить личный плагин только что созданного Site и отправить команду НОРДа ниже.
4. После распаковки с НОРДом открыть другой чат в том же проекте, подключить тот же плагин и отправить команду РИТМа.

Команда первого чата:

```text
Запусти ГР - НОРД. Прочитай целиком «01 - ГР - НОРД.md» из источников проекта. Прочитай сохраненную память через подключенный личный плагин этого проекта. Назови фактический этап и следующий шаг; если памяти нет, начни знакомство. Ничего не записывай без моего подтверждения.
```

Команда второго чата:

```text
Запусти ГР - РИТМ. Прочитай целиком «02 - ГР - РИТМ.md» из источников проекта. Прочитай сохраненные курс, годовую цель, спринт и неделю через подключенный личный плагин этого проекта. Продолжи существующий план; если данных нет, назови недостающее и предложи сначала завершить этот этап с НОРДом. Ничего не записывай без моего подтверждения.
```

Не утверждай, что скачивание в рабочую папку добавило Sources или установило навык меню. Не обещай автоматическое создание проекта, добавление источников и открытие чатов без доступного поддерживаемого механизма и фактического результата. Этот установочный чат не превращай в доказательство запуска двух отдельных специалистов.

## 5. Завершить отчетом о фактах

Верни: commit источника; URL и project_id созданной личной копии; фактическое имя/ссылку плагина; четыре файла и ZIP; результаты проверок; какие действия в Sources и настройках остаются владельцу. Не публикуй личный отчет, привязки, токены и данные в общий GitHub. Отдельно отметь, выполнялись ли два новых чата и проверка на телефоне. Полное прохождение не заявляй по одной успешной сборке.

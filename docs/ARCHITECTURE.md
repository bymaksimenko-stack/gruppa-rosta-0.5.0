# Архитектура MVP

## Главный принцип

Каждый участник разворачивает собственную независимую копию. Нет центрального аккаунта, общей базы, общего сервера, регистрации пользователей или подписочного слоя.

```text
GitHub-репозиторий участника
        │ исходники и миграции
        ▼
приватный ChatGPT Site ── D1 участника
        │                       ▲
        │ интерфейс             │ те же данные
        ▼                       │
личный дашборд          личный MCP-плагин
                                ▲
                    ┌───────────┴───────────┐
                    │                       │
             НОРД | Мой курс       РИТМ | 12 недель
```

## Поток данных

### Источники инструкций и источники личных данных

В основном тестовом формате 0.2.0 участник добавляет два файла `project/01 - ГР - НОРД.md` и `project/02 - ГР - РИТМ.md` в Sources облачного ChatGPT Project. Текст `project/Настройки проекта.md` между разделителями копирует в инструкции проекта. Команда запуска в отдельном чате выбирает один файл. Markdown не исполняется сам и не регистрирует навык меню. Доступность общих источников документирована OpenAI; фактическое чтение полных файлов из двух новых чатов и на телефоне проверяется отдельно.

GitHub хранит код и общие инструкции. Project Sources хранят инструкции выбранной версии. Приватный Site хранит личный курс, цели, планы, отчеты и краткую память НОРДа. Скачанная рабочая папка Work не становится Sources автоматически. Обновление инструкций не требует замены личного хранилища.

1. НОРД проводит распаковку, формирует «Мой маяк», Паспорт роста и реалистичную годовую цель.
2. Перед записью НОРД показывает итоговую формулировку и получает подтверждение.
3. НОРД вызывает `gruppa_rosta_v1_save_*`; Site проверяет личность ChatGPT и пишет только в запись этого пользователя.
4. РИТМ читает общий контекст через `gruppa_rosta_v1_get_dashboard`, строит 12-недельный цикл и недельный план.
5. РИТМ сохраняет спринт, задачи и отчеты через тот же персональный плагин.
6. Дашборд читает ту же запись D1. После перезагрузки видна актуальная ревизия.

## Границы специалистов

### НОРД

- горизонт 3–5 лет;
- желаемое будущее и факультативный нежелательный образ;
- точка А, ценности, сильные стороны и ограничения;
- реалистичная годовая цель;
- сверка курса раз в четыре недели;
- не ведет ежедневный список дел.

### РИТМ

- один измеримый 12-недельный результат;
- разные режимы нагрузки: щадящий, обычный, интенсивный;
- недельный фокус и проверяемые действия;
- ежедневная корректировка без бесконечного перепланирования;
- недельный отчет и рефлексия;
- не меняет жизненный курс без возврата к НОРДУ.

## Версионирование

### Память продолжения и дополнительный нативный навык

Пакет `plugins/gr-nord` содержит видимое имя «ГР - НОРД», русскую методологию и контракт памяти. Он не содержит личных данных и использует отдельно подключенный персональный MCP сайта. Локальная установка пакета не означает его публикацию или сохранение в браузерном аккаунте ChatGPT.

В начале нового чата НОРД вызывает `gruppa_rosta_v1_get_nord_context`: получает только курс, Паспорт, годовую цель, последнюю сверку и `nordMemory`, не всю историю отчетов. Подтвержденная память записывается через `gruppa_rosta_v1_save_nord_memory` с актуальной ревизией и перечитывается. Сайт отображает тот же `nordMemory`. Это первая компактная память продолжения; произвольная документная база знаний и поиск по ней еще не реализованы.

Схема JSON v2 добавляет `nordMemory`; мигратор читает v1, сохраняет все прежние поля и добавляет пустую память. Таблицы не меняются. Старый клиент с v1 не может затереть новые данные: запись проходит строгую проверку v2. Обновление состояния и архивирование предыдущей версии выполняются одной D1 batch-транзакцией с проверкой ревизии в самом UPDATE.

### Поля версий

- версия приложения: Git commit и Sites version;
- версия MCP-контракта: префикс `gruppa_rosta_v1_`;
- версия пользовательской схемы: `state.schemaVersion`;
- версия записи: монотонная `revision`;
- перед изменением текущая версия сохраняется в `growth_state_history`.

## Почему JSON-документ внутри D1

MVP персональный и не требует общей аналитики по людям. Один типизированный документ уменьшает риск частично обновленного состояния и упрощает экспорт/восстановление. Структуру проверяет Zod-схема. D1 также хранит ревизии и историю, поэтому обновление кода не стирает личные данные.

Если позже появится подтвержденная потребность в сложных выборках, сущности можно вынести в таблицы новой добавочной миграцией, не переписывая старые миграции.
